One read method, for `@_linked/core`'s `IDataset.readQuery` (core 2.46, DSL-JSON 1.10; the `@_linked/core` range is raised to `^2.46.0`). The generic provider's `selectQuery` and `askQuery` endpoints are replaced by one, `POST /call/@_linked/server/readQuery` (`@callable('public')`), which answers a select, a count or an ask: the body's kind is read before it is decoded (`readKindOfJSON`) and picks the access rule (`select` for a select or a count, `ask` for an ask), and the decoded query must be of that kind. A triples or terms read, a graph query and a write posted to it answer 400 (and roll back the caller's transaction they name). `/api/select` checks its read by kind the same way (an ask posted there is now answered, under the ask rule, where it was refused with 400; a body naming a transaction that does not decode now rolls it back). A store's function `read` rule sees `operation: 'ask'` for an ask, as it did from `askQuery`. `RemoteDataset` implements `readQuery` (select, count and ask go to the `readQuery` endpoint; triples and terms reads are refused without being sent) and declares `supports: ['ask']`, plus `'transactions'` after a ping that lists them. `graphQuery` and the write endpoints are unchanged. A client on an older `@_linked/server` gets `501 No provider` for its reads from this server.
